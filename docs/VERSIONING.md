# 《炼器宗》版本号管理规则

## 目的

《炼器宗》使用五段式页面版本号，展示当前所属大版本、开发变更层级以及生成该版本时的总代码行数。

该版本号是游戏页面和开发记录中的项目版本标识，不等同于Pull Request编号、Git提交数量或第三方包管理器版本。

## 格式

```text
v大版本.模块.组件.功能修改次数.总代码行数
```

形式化写法：

```text
vM.N.C.F.L
```

| 字段 | 含义 |
| --- | --- |
| `M` | 大版本，表示长期内容阶段 |
| `N` | 模块级修改计数 |
| `C` | 当前模块级周期内的组件级修改计数 |
| `F` | 当前组件级周期内的功能修改计数 |
| `L` | 生成版本时统计到的总代码行数快照 |

示例：

```text
v1.1.2.3.7982
```

表示项目处于v1大版本，已经记录到模块级计数1、组件级计数2、功能修改计数3，生成版本时共有7982行代码。

## 排序规则

版本先后只比较前四段，按照`M → N → C → F`的顺序逐段比较。

第五段`L`只记录代码规模，不参与版本排序。因此：

```text
v1.1.2.4.7600 > v1.1.2.3.7982
```

即使一次重构减少了总代码行数，只要前四段按规则递增，新版本就仍然大于旧版本。

## 递进规则

### 功能级修改

局部功能新增、修复、调整、测试补强或不改变组件边界的重构，使`F`增加1，并重新统计`L`。

```text
v1.1.2.3.7982
→ v1.1.2.4.8050
```

“任务触发条件调整”属于功能级修改。

### 组件级修改

新增组件，或改变一个组件的职责、状态模型、公开契约和主要行为，使`C`增加1，`F`归零，并重新统计`L`。

```text
v1.1.2.4.8050
→ v1.1.3.0.8420
```

“任务发布与状态跟踪”属于任务模块中的组件。

### 模块级修改

新增模块，或改变模块边界、跨组件数据流和模块级职责，使`N`增加1，`C`与`F`归零，并重新统计`L`。

```text
v1.1.3.0.8420
→ v1.2.0.0.9180
```

“任务系统”属于模块。

### 大版本修改

达到路线图定义的大版本目标时，使`M`进入对应大版本，`N`、`C`与`F`归零，并重新统计`L`。

```text
v1.8.6.12.24800
→ v2.0.0.0.25140
```

大版本内容目标以 [ROADMAP.md](ROADMAP.md) 为准。

## 修改层级判定

一次代码变更只提升一个层级。如果同一变更同时涉及多个层级，按照影响最高的层级递增一次：

```text
大版本 > 模块 > 组件 > 功能
```

判断顺序：

1. 是否达到或改变路线图中的大版本内容承诺？若是，按大版本处理。
2. 是否新增、删除或重新划分一个系统模块及其跨组件责任？若是，按模块处理。
3. 是否新增、删除或改变一个组件的契约、状态或主要职责？若是，按组件处理。
4. 其余代码修改按功能处理。

单个PR即使包含多个提交，也只生成一个最终页面版本号。若合并前主分支已经变化，必须基于最新主分支重新确定前四段并重新统计代码行数。

## 与Git和PR的关系

- 页面版本号不使用PR编号。
- 页面版本号不使用Git提交数量。
- 一个功能开发PR可以包含多个整理清晰的提交，但只提升一次页面版本。
- 非代码文档可以按仓库治理规则直接推送，且不提升页面版本。
- 所有代码变更必须通过PR，并在PR合并前包含正确的页面版本更新。
- Git提交哈希仍用于精确定位源码，但不作为五段式版本号的一部分。

## 代码行数统计

`L`表示当前Git工作树中受版本管理的有效代码行数快照。

统计原则：

- 统计应用源码、测试代码和以编程语言编写的构建配置。
- 排除空白行和纯注释行。
- 排除Markdown等文档、依赖目录、构建产物、覆盖率报告、锁文件、媒体资源和自动生成文件。
- 剧情文本、配方数据和其他内容数据是否纳入统计，由未来的统一统计脚本按文件类型固定决定，不允许每次发布手工改变口径。
- 格式化完成后再统计，并由统一的本地命令写入页面版本。

在工程脚手架建立后，仓库应提供唯一的本地版本生成命令，例如：

```text
pnpm version:stamp
```

该命令应完成以下工作：

1. 按指定层级递增版本。
2. 将低位计数按规则归零。
3. 使用固定口径重新统计总代码行数。
4. 写入游戏页面使用的权威版本文件。
5. 输出新旧版本，供提交者核对。

GitHub Actions保持禁用，因此版本生成和验证由本地流程完成。统计脚本是`L`字段的权威来源，开发者不得手工猜测代码行数。

## 权威版本位置

在应用脚手架建立后，应创建单一的版本权威文件。建议位置为：

```text
src/game/version.ts
```

页面显示、调试信息、导出存档元数据和错误报告都从该文件读取版本，不得在多个组件中复制版本字符串。

第三方工具若要求三段式包版本，可以使用仅满足工具约束的内部值；该值不构成另一套《炼器宗》游戏版本，也不得显示给玩家。

## 示例

假设当前版本为：

```text
v0.1.2.5.4260
```

不同变更对应的结果为：

| 变更 | 新版本示例 |
| --- | --- |
| 修复任务触发条件 | `v0.1.2.6.xxxx` |
| 重构任务状态跟踪组件 | `v0.1.3.0.xxxx` |
| 引入完整任务系统模块 | `v0.2.0.0.xxxx` |
| 完成首个正式大版本 | `v1.0.0.0.xxxx` |

其中`xxxx`必须由统一统计脚本替换为实际总代码行数。

## 规则变更

版本号格式、字段语义、排序规则和统计口径属于仓库治理规则。修改这些内容前，必须先更新本文档并明确记录迁移方式；已经发布的版本号不得被重新解释或重写。
